## Mission 1 — Assumption Ledger build (2026-11-06)

### Verified Hermes extension facts (HEAD 486f4a6a9918a4054373e33a200260ffd501645e, v0.23.0)
- Directory plugin layout: repo root needs `plugin.yaml` + `__init__.py` exposing `register(ctx)`.
  The loader (`plugins/plugin_loader.py::_load_plugin_module_locked`) puts the plugin dir on the
  module path and also loads every top-level `*.py` in that dir as a submodule — so a sibling
  package dir (`ledger/`) works with a plain `from ledger import ...` inside the plugin.

  handler is `fn(raw_args: str) -> str | None`. `args_hint` needed for Discord arg field.

- Storage: `plugins.plugin_storage.plugin_data_dir(name)` / `plugin_db(name)` is the sanctioned

### Two real defects found by the adversarial suite (both fixed, both non-vacuous)
1. **Transient error softened a contradiction.** `status_after_check` returned
   `STALE if had_fresh_evidence` on any error, so DNS/500/timeout degraded `INVALIDATED` → STALE
   and **unblocked** decisions depending on it. The existing oracle O10 only exercised the
   `unsupported` check kind, which returns *before* `status_after_check` is consulted — so the
   oracle passed while the dangerous path was broken. Fix: error returns `INVALIDATED` unchanged.
   Regression test reverts cleanly to the bug.
2. **`git_clean` counted untracked files.** The ledger's own `ledger.db` made any repo look dirty.
   Fix: report untracked as observed evidence, don't invalidate; `include_untracked: true` opts in.
   Note the original test *asserted* the buggy behaviour (untracked → FAIL), so it had to change.

### The 403 is a scope problem, not a permission-grant problem
`x-oauth-scopes:` is **empty** — the token has *zero* scopes. GitHub's response header says
`x-accepted-oauth-scopes: repo`. A fine-grained token with no scopes can push to repos it owns
but cannot open a PR on someone else's repo. Do not ask for "Administration: write"; ask only
for PR creation on the upstream repo — or have the owner click the compare link.

### CORRECTION to my Mission 2 claim (important)
I previously said a "bogus SHA" made the catalog test fail, implying it validated the pin.
**It does not validate the pin.** Measured against the real upstream test:

| injected `sha:` | result |
|---|---|
| all-zeros 40 hex | FAIL |
| all-ones 40 hex | **PASS** |
| 39 / 41 chars, non-hex | FAIL |
| uppercase hex | PASS |

Mechanism: YAML parses all-zeros as the **integer `0`**, so `^[0-9a-f]{40}$` fails on the
*string* form. All-ones overflows YAML's int range and stays a string → passes. The test checks
**format only and never resolves the commit**; a well-formed nonexistent SHA passes.
→ Always verify a pinned SHA by cloning and checking out the exact commit, never by the test.
Lesson: when a check "passes for the wrong reason", read the raw assertion output (`got 0` was
the tell) instead of trusting the verdict.
